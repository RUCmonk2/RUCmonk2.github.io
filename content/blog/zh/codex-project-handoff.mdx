短任务只需要一句清楚的提示词，长期项目却会遇到另一个问题：对话会结束，资料会变多，新的 AI 不知道上一轮为什么这样做。我的解决办法不是写一份越来越长的总提示词，而是把项目状态放回项目本身。

## 一个稳定的入口

项目根目录保留一份交接 README。它不负责收纳所有细节，只回答五个问题：

- 当前主线是什么；
- 哪些文件最重要；
- 临时资料应该怎样处理；
- 还有哪些遗留问题；
- 下一步最值得做什么。

新一轮对话开始时，我先让 Codex 阅读这份文件并复述当前状态。复述是一个很便宜的校验步骤，能在修改文件前发现理解偏差。

## 把状态拆成几种不同记录

当项目变复杂后，一份 README 仍然会过载。我会在语境交接目录里继续拆分：

- `CURRENT.md` 记录现在进行到哪里；
- `DECISIONS.md` 记录已经做出的选择及理由；
- `FILE_MAP.md` 说明重要文件各自负责什么；
- `OPEN_QUESTIONS.md` 留下尚未解决的问题；
- `JOURNAL.md` 只保留简短的阶段记录。

这些文件不是日记，也不应复制整段聊天。它们的价值在于让下一位执行者快速恢复判断所需的上下文。

## temps 只做临时区

`temps/` 用来接收还没判断用途的截图、草稿、导出文件和中间产物。这里的规则很简单：

1. 新资料先放进临时区，不直接混入正式目录。
2. 使用前先判断它应该归档、转写还是删除。
3. 真正有长期价值的内容移入正式位置，并更新文件地图。
4. 不把临时区作为永久资料库，也不将其中内容发布到网站。

这种分区降低了误操作，也让正式目录保持可读。

## 先对齐，再执行

我习惯在较大的改动前要求 AI 说明它理解到的目标、准备修改的范围以及验证方法。执行完成后，再把真正改变项目状态的信息写回交接文件。

这样做不会消除所有错误，但能让错误更早暴露，也让一次对话的成果不会随着对话结束而消失。
